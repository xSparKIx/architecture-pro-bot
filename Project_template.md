### 4. Рекомендация по конфигурации сервера (для продакшена в EKS)

**Архитектура**: Разделить на микросервисы в Kubernetes (EKS).

**Сервис эмбеддингов:** 2-4 реплики. CPU: 4 ядра, RAM: 8-16 ГБ на pod. Модель: intfloat/multilingual-e5-large.

**Сервис LLM:** 2 реплики с GPU. CPU: 4 ядра, RAM: 16 ГБ, GPU: NVIDIA RTX 4090 (24GB) или A10 (24GB) в cloud. Модель: Qwen2.5-Coder-7B-Instruct (4-битная квантизация).

**Сервис RAG-бэкенда и векторной БД:** ChromaDB в persistence-режиме, развернутая как StatefulSet. CPU: 4 ядра, RAM: 16 ГБ, SSD: 50 ГБ.

**Итоговая конфигурация кластера EKS:** ~16 CPU ядер, 64-96 ГБ ОЗУ, 1-2 мощных GPU. Начинать можно с CPU-only для эмбеддингов и малой LLM.

### Итоговые рекомендации для QuantumForge:

#### Вариант 1 (Оптимальный для безопасности и контроля):

**LLM:** Локальная, квантизованная Qwen2.5-Coder-7B-Instruct-GGUF (запуск через Ollama или vLLM).

**Эмбеддинги:** Локальный Sentence-Transformer (intfloat/multilingual-e5-large).

**Векторная БД:** ChromaDB (в режиме in-memory с сохранением на диск, развернутая как отдельный сервис).

**Инфраструктура:** Выделенный GPU-сервер в приватном облаке (или on-premise) с интеграцией в существующий EKS. NVIDIA RTX 4090 24GB или эквивалент в cloud (AWS G5, Inferentia).

**Почему лучший:** Максимально соответствует требованиям конфиденциальности (SOC 2), дает полный контроль, масштабируемо, использует сильные стороны команды R&D. Баланс стоимости, качества и безопасности.

#### Вариант 2 (Экономный старт, MVP):

Всё то же самое, но LLM и эмбеддинги — на мощных CPU (например, на инстансах c6i.4xlarge в AWS). Без GPU.

**Почему:** Чтобы быстро проверить гипотезу и собрать метрики, прежде чем инвестировать в GPU. Подойдет для первых десятков пользователей.

#### Вариант 3 (Полностью облачный, но приватный (не рекомендуется для данного кейса)):

Использование облачных VM с GPU (AWS, GCP) и развертывание там же всей локальной стека (Ollama + ChromaDB).

**Почему не рекомендуется:** Хотя данные физически могут не покидать cloud провайдера, это сложнее для аудита SOC 2, дороже в долгосрочной перспективе, чем on-premise, но проще в управлении, чем свой дата-центр. Может быть рассмотрен, если в компании строгая политика "только cloud".

### **Вывод**
Для создания бота я планирую использовать вариант 1 (локальные модели + ChromaDB), так как он единственный полностью удовлетворяет критически важному требованию конфиденциальности данных для продукта QuantumForge, соответствует их техническим возможностям (команда R&D) и бизнес-целям (сокращение затрат в долгосрочной перспективе, масштабируемость).

## Задание 3. Создание векторного индекса базы знаний

### Описание проекта

Создание векторного индекса для внутренней базы знаний QuantumForge Software с использованием RAG-архитектуры.
Также была добавлена предварительная проверка данных, если данные являются опасными или подозрительными, то они будут исключены из индекса.

### Используемые технологии

#### Модель эмбеддингов
- **Название**: `paraphrase-multilingual-MiniLM-L12-v2`
- **Репозиторий**: https://huggingface.co/sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2
- **Размерность**: 384
- **Особенности**: 
  - Оптимизирована для поиска семантически близких предложений (перефразировок, синонимичных высказываний).
  - Работает с более чем 50 языками, включая русский, английский, китайский, немецкий, французский и многие другие. Ключевое преимущество — она сопоставляет смысл между языками (кросс-лингвально). То есть вектор для "Hello" будет близок к вектору для "Привет".
  - Облегченная архитектура, производная от моделей типа BERT/RoBERTa. Она сохраняет высокое качество, но значительно меньше и быстрее благодаря дистилляции (обучению у "учителя").

#### Векторная база данных
- **Тип**: ChromaDB
- **Режим**: Сохранение на диске
- **Метрика расстояния**: Косинусное сходство
- **Преимущества**: 
  - Встроенное хранение метаданных
  - Простой API
  - Поддержка фильтрации

#### Обработка документов
- **Чанкинг**: Рекурсивное разбиение по семантическим границам
- **Размер чанка**: 500 токенов
- **Перекрытие**: 100 токенов
- **Сохранение**: Полные метаданные источника и позиции

## Задание 6. Автоматическое ежедневное обновление базы знаний

### Описание
Сервис автоматически обновляет базу знаний каждый день в 24:00.

### Что происходит при каждом запуске:
1. Загружается состояние из `update_state.json`
2. Для каждого файла вычисляется текущий MD5 хеш
3. Сравнивается с сохраненным хешем
4. Если хеши разные → файл изменился → добавляем в список обновлений
5. Сохраняем новые хеши в состояние
6. Удаляем из состояния файлы, которых больше нет в папке
7. Сохраняем файл `update_summary.json` с списком измененных данных

### Пример состояния:
```json
{
  "last_update": "2026-01-25T19:13:34.545702",
  "file_hashes": {
    "/home/sparki/projects/architecture-pro-bot/task6/../task2/knowledge_base/place_Hoth.md": "871064ea51d9540fb59bcce34d89e004"
  },
  "total_files": 1,
  "total_chunks": 3
}
```

### Пример файла с изменениями:
```json
{
  "timestamp": "2026-01-25T19:12:07.732618",
  "files_processed": 1,
  "chunks_created": 3,
  "duration_seconds": 0.06,
  "tracked_files_count": 1,
  "file_list": [
    {
      "path": "/home/sparki/projects/architecture-pro-bot/task6/../task2/knowledge_base/place_Hoth.md",
      "status": "new",
      "hash": "871064ea51d9540fb59bcce34d89e004",
      "old_hash": null
    }
  ]
}
```

## Задание 7. Аналитика покрытия и качества базы знаний

### Проблемные места

Бот переодически выбирает некорректные источники для получения информации, зачастую попадают источники, которые напрямую не связаны с вопросом. Из-за этого в контекст попадает информация, которая является лишней и бот начинает на ее основе додумывать ответ. Например в случае с "Emo Redemption Arc" бот подбирает некорректные источники и додумывает контекст, а не отвечает прямым текстом, что что-то не так. Метод вычисления уверенноси в ответе также нуждается в доработке для обеспечения более полной и точной оценки. Также бот выдает не стабильные ответы и в разных запусках может давать разные ответы на один и тот же вопрос, который может проходить или не проходить проверку.

#### Для устранения такой проблемы необходимо:

- Дополнить базу знаний необходимой информацией
- Поправить промпт, чтобы бот опирался только базу знаний
- Переработать данные, на которых происходит подготовка векторной базы данных
- Возможно подобрать более подходящую модель для формирования чанков
- Также необходимо дополнить базу знаний контентом на разных языках, чтобы бот лучше понимал синонимы и контекст
- Добавить модель re-ranking
- Попробовать уменьшить размер чанка до 300 токенов для улучшении точности и полноты ответа
- Переработать метод вычисления уверенности в ответе

Изначально для анализа контента использовалась модель `llama2`, но она переодически галюцинировала и всегда считала, что корректно выдает ответ относительно передаваемоей ей информации, поэтому в последствии она была заменена на `mistral:7b-instruct`, которая более точно следует промпту и более продуманно выдает ответ.

#### Где может происходить сбой

Проблемы могу происходить на моменте передачи вопроса от пользователя в сервис RAG. Пользователь может передавать некорректный или опасный запрос. Для устранения этого узкого места необходимо добавить предварительную валидацию вопроса и проверку его безопаности.
